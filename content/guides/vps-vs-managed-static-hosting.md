A VPS is worth considering when you need to run and maintain server software.</p></section><article class="prose"><h2>Begin with what runs after a visitor arrives</h2>
<p>If your deployment produces HTML, CSS and images, managed static hosting is a sensible option to investigate first. If the website needs a persistent process, a database or background workers, describe those components before selecting hosting. Adding an AI chat feature does not automatically turn the project into a GPU server: it may call an external model API instead.</p>
<p>Cloudflare documents Pages as a website deployment platform and separately documents its Functions capability. That means a static project and a project using server-side functions can have different limits and operating costs. Do not treat a provider's free entry point as a guarantee that every future feature remains free. Read the documentation for the features you actually plan to enable.</p>
<h2>Compare responsibility as well as features</h2>
<div class="table-wrap"><table><thead><tr><th>Approach</th><th>Useful question</th><th>Responsibility to plan</th></tr></thead><tbody>
<tr><td>Managed static hosting</td><td>Can the site be generated before deployment?</td><td>Build reproducibility, custom domain, redirects and any function usage.</td></tr>
<tr><td>VPS</td><td>Do you need control over persistent software?</td><td>Operating system updates, application security, monitoring and recovery.</td></tr>
<tr><td>Managed inference endpoint</td><td>Do you need to serve a model through an endpoint?</td><td>Model choice, hardware configuration, scaling and inference billing.</td></tr>
</tbody></table></div>
<p>With a VPS, you maintain the operating system and running app. A managed platform handles some of that work but sets limits on builds, functions and other features. Compare the maintenance you can take on with the features your site needs.</p>
<h2>Keep browser code and secrets apart</h2>
<p>Anything delivered in a static page can be inspected by visitors. Keep private API credentials out of generated HTML, public repositories and downloadable JavaScript. If a feature requires a secret, use an appropriate server-side component and its documented secret management. Limit requests and spending there, rather than relying only on a button being hidden in the browser.</p>
<p>A public chat or generation endpoint needs an abuse plan. Consider repeated requests, large inputs and retries. A monthly editor subscription is not payment for calls made by website visitors. Set a usage budget before making the feature public, and make failure states understandable. A page should be able to explain a temporary limit without repeatedly triggering another paid request.</p>
<h2>Plan a move before it becomes urgent</h2>
<p>Keep the source repository, build command, environment requirements and domain settings documented. For a static site, check that a fresh build produces the same routes and canonical domain. For an application, add a database export and restore procedure. A successful deploy alone does not prove you can recover from a lost server or move away from a platform.</p>
<p>Compare renewal costs and the recurring work needed to operate the site. Include the features you actually require instead of assuming every optional add-on belongs in the budget.
